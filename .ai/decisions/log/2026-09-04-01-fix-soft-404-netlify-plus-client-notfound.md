# 2026-09-04 — Fix soft-404s with a real Netlify 404 plus a client-side not-found screen

**Context:** Issue #78 (part of the SEO checklist in #74) flagged that `netlify.toml`'s blanket `/* → /index.html status=200` catch-all serves HTTP 200 for any nonexistent URL — a typo, a stale link, or a removed world/lesson — with React Router's own catch-all then silently redirecting to `/` client-side. Google Search Console flags this pattern as a "soft 404," which can hurt crawl budget and indexing signal quality. The issue asked for a decision between an edge-level fix (split the redirect so only known route prefixes rewrite to 200, everything else gets a real static 404), a client-side fix (make the unmatched-route result clearly a "not found" page instead of a silent bounce, even though the HTTP status stays 200), or a combination.

**Decision:** Combination, scoped to what the app actually has. The app has exactly two real top-level route prefixes: `/` (prerendered landing) and `/app*` (SPA shell). `netlify.toml`'s catch-all now serves a real static `public/404.html` with `status = 404` for anything outside those two prefixes, fixing the actual GSC complaint for typo/stale/removed top-level links. Separately, a path that *is* under `/app*` (so it must stay HTTP 200, since `/app*` is a genuinely working prefix) but doesn't match any defined React Router route — e.g. a bookmarked link to a since-removed world or lesson — still can't get a real HTTP 404 from the edge, since Netlify has no visibility into the client-side route table. For that remaining case, `src/App.tsx`'s top-level catch-all `<Route path="*">` now renders a dedicated `NotFoundScreen` (clear messaging, `noindex` meta while mounted) instead of silently redirecting to `/`, rather than leaving the visitor wondering why they landed on the marketing page.

**Alternatives rejected:**
- Netlify fix only — leaves the silent `<Navigate to="/" />` bounce for stale in-app links unexplained; cheap to also fix while the route file is already being touched.
- Client-side fix only — does not change the raw HTTP status for genuinely unknown top-level URLs, which is the actual mechanism GSC flags. Would not close #78.
- Enumerating every world/lesson id as its own Netlify redirect rule — massive maintenance burden for what two prefix rules already cover; every new world would need a `netlify.toml` edit.
- Giving `/app*` itself a real edge-level 404 for unmatched sub-paths — would require duplicating the React Router route table into `netlify.toml`, impossible to keep in sync from edge config alone. This is the standard "the edge can't know the client's routes" problem every SPA has; the client-rendered not-found screen plus `noindex` is the accepted mitigation.

**Consequences:** Any genuinely unknown top-level URL now returns a real HTTP 404 with a small on-brand static page, closing the GSC soft-404 flag for those. A bookmarked deep link into a removed world/lesson still returns HTTP 200 (unavoidable without duplicating the route table at the edge) but now renders a clearly-labeled "not found" screen with `noindex` instead of silently teleporting to the landing page — better for both crawlers that do reach it and for a real visitor. `public/404.html` is a new static file authored outside the Vite/React build (English only, same category as `index.html`'s own hardcoded SEO meta tags) and must be kept in sync by hand if the brand's dark theme colors change; no build step currently regenerates it.
