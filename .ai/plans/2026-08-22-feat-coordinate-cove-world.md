## Decision

Add exactly **two read-only sensor blocks** — `sensor_row` and `sensor_col` — that return the character's **1-based** row and column, matching the row/column labels drawn on the grid. To make them meaningful, `parseCodeToActions` becomes a **headless simulation** that reuses the existing `applyAction` reducer, so a sensor read during code generation returns exactly the position the animation will show. Two new termination guards (an action-cap throw and Blockly's `INFINITE_LOOP_TRAP`) make sensor-driven `while` loops provably terminate. Ship the bonus world 🧭 **Coordinate Cove / Teluk Koordinat** (ages 10–13) with a tutorial plus 10 lessons on top of that surface.

### 1. Block surface

| Block | Label (EN / ID) | Output | Generated JS |
|---|---|---|---|
| `sensor_row` | 🧭 my row / 🧭 barisku | `Number` | `currentRow()` |
| `sensor_col` | 🧭 my column / 🧭 kolomku | `Number` | `currentCol()` |

- Both are **value blocks** (`output: 'Number'`, no `previousStatement`/`nextStatement`), so they can only be plugged into a comparison, an arithmetic block, or a variable setter. They cannot be dropped into a statement stack on their own.
- Both are **read-only**. There is deliberately no setter, no teleport, and no "distance to marker" block: a setter would let a lesson be solved without navigating, and a distance block would answer the question the world is asking.
- Values are **1-based** and identical to the labels rendered on the grid gutter. A child who reads "Row 3" off the chart and types `3` into a comparison gets the behaviour they expect. The engine stays 0-based internally; `COORD_ORIGIN = 1` is applied at the sensor boundary only.
- A new toolbox category `sensors` (🧭 Position / 🧭 Posisi) carries both blocks. As with `variables`/`logic`/`lists`, selecting it also surfaces the Math category so a number can be compared against.

### 2. Sandbox exposure

`parseCodeToActions` builds its `new Function(...)` with exactly seven **usable** named parameters, and a `'use strict'` prologue on the body:

```
moveRight, moveLeft, moveUp, moveDown, currentRow, currentCol, __tick
```

- `currentRow` / `currentCol` are zero-argument closures over the local simulation state. They return a `number` and nothing else — no object, no reference to the lesson, no reference to the state.
- `__tick` is the loop-trap counter described in §3. It takes no argument and returns nothing.
- `collect` is **not** in this list and never was after `fix-collect-item-remove` — items are auto-collected by `applyAction` when the character enters their cell. INV-G4's text is corrected to match the code as part of this change (a correction of a stale invariant, not a weakening: the exposed set shrinks by `collect` and grows by three names that are all pure and bounded).

`new Function` compiles its body in **global** scope, so listing seven parameters is not by itself enough — the body could still resolve `window` or `fetch` by name. So the constructor is also handed a `SHADOWED_GLOBALS` list of identifiers as extra parameters and called without arguments for them, binding each to `undefined` for the whole body: `globalThis`, `window`, `self`, `top`, `parent`, `frames`, `document`, `location`, `history`, `navigator`, `fetch`, `XMLHttpRequest`, `WebSocket`, `EventSource`, `sendBeacon`, `localStorage`, `sessionStorage`, `indexedDB`, `caches`, `cookieStore`, `Function`, `require`, `importScripts`, `process`, `Worker`, `SharedWorker`, `WebAssembly`, `postMessage`, `open`, `alert`, `confirm`, `prompt`, `setTimeout`, `setInterval`, `requestAnimationFrame`, `queueMicrotask`. `'use strict'` leaves `this` undefined, closing the other easy route to the global object. `eval` and `import` are absent because neither is a legal parameter name (`eval` is banned in a strict-mode parameter list, `import` is a reserved word); direct `eval` resolves through this same shadowed scope, so it reaches the same `undefined` bindings.

This is defence in depth for a **closed input space** — every line executed here is generated by blocks this app defines — not a hardened security boundary. A prototype walk such as `[].constructor.constructor('return this')()` cannot be shadowed away, and no amount of parameter shadowing changes that. What the shadowing does buy is that INV-G4's sentence is now literally true of the identifiers it names, and a test asserts it.

**INV-G4 restated:** Block-generated code runs in a `new Function(...)` context under `'use strict'`. Only the four movement verbs (`moveRight`, `moveLeft`, `moveUp`, `moveDown`), the two read-only position sensors (`currentRow`, `currentCol`), and the loop guard (`__tick`) are usable in scope. `window`, `document`, `fetch`, `localStorage`, and every other identifier in `SHADOWED_GLOBALS` resolve to `undefined`.

### 3. Action-cap behaviour (INV-G3)

Today the movement closures silently drop actions once `MAX_ACTIONS` is reached. With sensors that becomes a hang: `while (currentRow() < 5) { moveDown(); }` would spin forever if the moves stopped registering while the position froze. Three guards replace the silent drop, and all three unwind by throwing a private sentinel that only `parseCodeToActions` catches:

| Guard | Trigger | Result |
|---|---|---|
| Action cap | a movement verb is called when `actions.length === MAX_ACTIONS` (200) | stop generating; return the 200 actions with `stopped: 'action-cap'` |
| Crash halt | a movement verb produces `status: 'crashed'` in the simulation | record the crashing action, stop; the animation replays it and crashes identically |
| Loop trap | `__tick()` — injected by `javascriptGenerator.INFINITE_LOOP_TRAP` into every loop body — is called more than `MAX_LOOP_TICKS` (10 000) times | stop generating; return with `stopped: 'loop-cap'` |

The loop trap is what makes a **non-moving** infinite loop (`while (true) {}`, or a `while` whose body has no move block) stop cleanly — the action cap alone cannot see it, because no action is ever pushed. 10 000 ticks of an empty loop body run in well under a frame, so the tab never freezes. This closes a hang that already existed in Crystal Caves and Time Portal, which both ship `controls_whileUntil`.

`MAX_ACTIONS` itself is unchanged at 200, and no execution path can exceed it: every action is pushed through the single guarded `pushAction` helper.

The sentinel is a module-private class, never rethrown, and never surfaced as `error`. A halted run is not a code error — the child sees their boat sail 200 steps and miss, or sees the friendly new `game.fail.loop` message when the loop produced no movement at all.

### 4. Star scoring

Sensor blocks are ordinary Blockly blocks, so `workspace.getAllBlocks(false).length` already counts them — **yes, they count toward `optimalBlockCount` and `starThresholds`**, and every Coordinate Cove threshold in this plan is authored from the full block count of the canonical solution (comparison and number blocks included).

Because a sensor-driven loop always costs more blocks than hardcoding the same number of moves, block count alone would reward *not* learning the concept. `requiredCategories` is the existing answer: `sensors` is registered in `CATEGORY_BLOCK_TYPES` (`['sensor_row', 'sensor_col']`), and every lesson that teaches position reading sets `requiredCategories: ['sensors', ...]`, capping a hardcoded route at 1 star with an explanatory line in the reward modal.

### 5. Accessibility

`Lesson` gains an optional `showCoords?: true`. When set, `GameGrid` renders:

- a **column header strip** above the grid numbered `1..gridCols`, and a **row gutter** to its left numbered `1..gridRows`, both using the world accent colour at a readable weight;
- a **live position readout** under the grid — "Row 2 · Column 5" — through `t('game.coords.readout', { row, col })`, updated on every animation step.

The coordinate is therefore *read*, never *counted*: a child who cannot count cells reliably (and a screen-reader user reading the readout text) still knows exactly where the boat is. Labels are plain digits, so they need no translation; the words "Row" and "Column" come from `t()`. The gutter is sized from `cellSize`, so it scales with the existing responsive grid and adds no fixed-width container (INV-I2).

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| A single `sensor_pos` block returning `[row, col]` | Forces list indexing to read a coordinate, which belongs to Time Portal, not here. Two scalar blocks plug straight into `logic_compare`. |
| 0-based sensor values | The grid gutter would read `0..n-1` while every lesson says "Row 3". Off-by-one confusion would swamp the concept the world teaches. |
| Sensors that return the *distance to the nearest marker* | Answers the navigation question for the child. The world is about reading your own coordinate, not being told where to go. |
| A `set_position` / teleport block | Lets a lesson be won without navigating, and would break INV-G1/INV-G2 unless it re-ran every bounds and obstacle check anyway. |
| Keep `parseCodeToActions` stateless and evaluate sensors against `startPos` | Every sensor read would return the same value, so every condition would resolve identically — exactly the fake condition the roadmap forbids. |
| Simulate movement with a second copy of the movement rules inside the parser | Two implementations of bounds/obstacle/collection logic would drift. Reusing `applyAction` makes the simulation and the animation the same code. |
| Only cap actions, no loop trap | A `while` loop with no move block inside would hang the tab. Blockly's own `INFINITE_LOOP_TRAP` is the supported mechanism. |
| Surface the loop trap in the code view | `__tick();` in every loop body confuses a child reading their own code. The view strips it; execution keeps it. |
| Author the world in a follow-up PR, ship engine only | Sensor blocks with no lesson using them are unreviewable dead code. The request asked for the world. |

### Content audit — Coordinate Cove

| # | Core mechanic | Scenario | Blocks | Notes |
|---|---|---|---|---|
| 0 | read a labelled coordinate, move to it | first sight of the chart | 2 | tutorial, no stars |
| 1 | read an absolute coordinate | marker on open water | 4 | move only |
| 2 | compute a coordinate *relative* to a landmark | island at R4C2 | 6 | move only; the island is a real obstacle |
| 3 | store a step count in a variable | measured run of buoys | 5 | variables + repeat |
| 4 | **update** a stored value between legs | widening gap between two markers | 12 | the update changes the second leg |
| 5 | loop until a **row** sensor reaches a target | descending a reef wall | 5 | first sensor lesson |
| 6 | loop **until** a **column** sensor equals a target | sailing a channel | 5 | `UNTIL` mode + equality, not `<` |
| 7 | two sensor loops, order forced by obstacles | reef bar across the top row | 10 | right-first crashes |
| 8 | three sensor loops visiting coordinate pairs | three chart markers | 15 | same axis revisited at a new target |
| 9 | fix an off-by-one in a supplied sensor loop | short-stopped survey run | 5 | `isBuggy`, workspace pre-loaded |
| 10 | four-leg route combining every leg type | the deep chart | 20 | obstacles punish overshoot |

No two rows share both a mechanic and a scenario. Lessons 5 and 6 are the closest pair and are separated on three axes: row vs column, `WHILE`+`<` vs `UNTIL`+`=`, and reef wall vs channel. Difficulty rises through cognitive load — no sensor → one sensor loop → two axes → three legs → debugging someone else's loop → four legs with punishing obstacles — not through bigger grids alone.

## Implementation notes

- The parse simulation reuses `applyAction` rather than reimplementing movement, so INV-G1/INV-G2 hold in the parser by construction.
- `__tick` is prefixed with underscores and is never shown to a child: the code view strips the trap line before rendering.
- `game.fail.loop` was added because an infinite loop with no movement previously fell through to `game.fail.noactions` ("No movement blocks detected"), which is misleading when the child *did* add a move block inside a loop that never ran.
- **Deviation from the plan as first drafted:** §2 originally claimed the seven-parameter list was sufficient to keep globals out of scope. It is not — `new Function` compiles in global scope. `SHADOWED_GLOBALS` and the `'use strict'` prologue were added during implementation so the invariant holds, and the plan text above now describes what shipped, including what the technique does *not* guarantee.
- Every canonical solution in the content audit was verified against **real Blockly**, not just hand-written JavaScript: each lesson's solution was built as a serialised workspace, run through `javascriptGenerator.workspaceToCode`, and replayed. All eleven matched their authored `optimalBlockCount` exactly and won their lesson. That run also confirmed the two generator assumptions the test suite encodes — `INFINITE_LOOP_TRAP` emits `__tick();` as the first statement of every loop body, and `controls_whileUntil` in `UNTIL` mode emits `while (!(…))`. The probe needed `jsdom` to run Blockly headlessly, so it was not kept as a test: the plan lists no new dependency, and `tests/coordinateCoveLessons.test.ts` asserts the same generated strings without one.
- `biome ci` reports "Checked 1 file" — `biome.json` scopes `files.includes` to `src/*.js` and `scripts/*.mjs`, so no TypeScript in this repo is linted by it. Pre-existing configuration, untouched here.
